# External Bitcoin integration boundary

Verified **1 October 2026**. This is implemented testnet preparation code, not a claim that every route is live, audited, or that a funded deposit/withdrawal cycle has completed. Mainnet writes, BTC broadcasting, private-key storage in the application, and protocol account creation are not exposed by this package.

## Delivered modules

`integrations/bitcoin` is a separate ESM TypeScript package with exact SDK dependency pins and lazy SDK imports. Its public request/quote/plan objects are JSON serializable; sessions keep providers and authorization state in memory. The React page is `frontend/src/components/bitcoin/BitcoinRoutes.tsx`.

| Route | Implemented | Still required for complete execution |
|---|---|---|
| Babylon Signet / bbn-test-6 | Live chain/parameter/provider discovery; wallet and confirmed-UTXO checks; official SDK staking PSBT; reviewed-plan digest; returned-PSBT signature guard; official SDK early-unbond and expired-lock recovery plans | Funded fresh Signet and BABY test accounts; pre-staking registration including signed slashing transactions and proof of possession; covenant verification; BTC confirmations; reward/delegation monitoring; actual early and expired recovery |
| Lombard Signet → Sepolia LBTC | Live SDK quote; pinned test token and test partner; account/chain binding; exact EIP-712 fee authorization guard; stored-signature verification; SDK-generated address with independent API registration checks | Actual sandbox authorization/address registration, funded BTC transfer, mint/issuance confirmation, destination gas and full redemption evidence |
| Solv | Fixed official documentation handoff with external threshold-custody disclosure; no deposit address or fabricated transaction | Official partner enrollment, exact chosen strategy/chain/token and a supported public BTC deposit/redemption environment |
| Native Stacks BTC | Separate asset/lifecycle boundary in capability registry | Current PoX-5 integration is tracked separately in `integrations/pox5`; do not translate it into an sBTC vault adapter |

The current Lombard LBTC product must not be described solely as Babylon staking: current product documentation describes a covered-call strategy and consortium custody. The SDK operation is named `btc.stake`, but its name does not erase strategy, custody, issuance or redemption risks. [Official product FAQ](https://docs.lombard.finance/use/faq).

## Babylon implementation

The current official package is `@babylonlabs-io/btc-staking-ts@2.8.6`, with `bitcoinjs-lib@6.1.7` and `@babylonlabs-io/babylon-proto-ts@1.22.1` peers. The official reference explains pre-staking registration, covenant verification, staking broadcast, unbonding and withdrawal as separate steps. A plain BTC transfer or a locally constructed staking output is not enough to become an active delegation. [SDK and usage source](https://github.com/babylonlabs-io/btc-staking-ts/blob/main/docs/usage.md), [official reference application](https://docs.babylonlabs.io/developers/babylon_genesis_chain/dapps/simple_staking_dapp/).

`fetchBabylonSignetContext()` verifies the Signet genesis hash and `bbn-test-6` node identity, checks Babylon's Bitcoin light-client height against Signet, fetches all returned parameter versions and finality-provider states, and compares the latest API parameter set to LCD committee, bounds, timelock, slashing and fee values. Observations expire after two minutes. Providers must be active and distinct from staker/covenant keys. Historical parameter versions remain available for recovery.

`buildBabylonStakePlan(request)` uses the real SDK `Staking` constructor, `createStakingTransaction` and `toStakingPsbt`. It accepts native SegWit/Taproot funding only, derives the expected wallet script from the public key, parses each previous transaction, and matches transaction ID, output index, value and script. It rejects duplicate funding, fractional/unsafe amounts, mismatched networks, stale data, excessive fees, foreign change and invalid timelocks. It independently sums actual selected inputs/outputs and binds the resulting plan to a SHA-256 review digest. The output is explicitly `broadcastAllowed:false` and `nextStep:'babylon-pre-staking-registration'`.

`validateReturnedStakePsbt` verifies unchanged unsigned inputs, outputs, sequences and locktime; unchanged UTXO amounts/scripts and PSBT metadata; safe ALL/default signature modes; the current wallet; plan integrity/expiry; and all cryptographic input signatures. It deliberately rejects finalized PSBTs. It is a validation utility, not permission to skip Babylon registration.

`buildBabylonRecoveryPlan` uses the exact saved transaction and historical parameters. Early unbonding remains dependent on authentic covenant signatures and delegation state. Expired withdrawal requires the supplied confirmed height to have reached the lock duration and pays only the original wallet script. Confirmation height/UTXO status must be independently rechecked by a node before any future signing/broadcast layer; unsigned recovery planning is not confirmation proof. A plan digest detects accidental/substituted review state, not a malicious application that can recompute the digest.

Official network documentation confirms Signet, `bbn-test-6`, LCD/RPC endpoints and committee; it includes an older node snapshot version, so the implementation reads live parameters instead of hardcoding that snapshot. [Network reference](https://docs.babylonlabs.io/developers/bitcoin_staking/networks/signet/).

## Lombard implementation

`prepareLombardStake({amountBtc,recipient,expectedChainId:11155111},provider)` calls the real `@lombard.finance/sdk@5.9.0` with `Env.testnet`, `partnerId:'test'`, `Chain.BITCOIN_SIGNET`, `Chain.SEPOLIA`, and `AssetId.LBTC`. The executing SDK transaction resolver selects `0x107fc7d90484534704dd2a9e24c7bd45db4dd1b5` (LBTC, 8 decimals). Its separate display catalog lists `0xc47e4b3124597fdf8dd07843d4a7052f2ee80c30`, whose on-chain symbol is stLBTC. Both entries are pinned explicitly; neither is a caller-selected address. Any change to this known SDK pair fails closed. The quote and UI display the executing receipt token, not the mismatched catalog token. The quote includes actual SDK minting fee, estimated LBTC and recipient, but explicitly states `minimumOutputEnforced:false`. Ratio changes and BTC network fees can affect receipt/cost. [Official sandbox](https://docs.lombard.finance/build/sdk/start-here/testing-and-sandbox), [BTC stake action](https://docs.lombard.finance/build/sdk/capabilities/bitcoin/btc-stake).

Preparation does not sign. A deliberate `session.authorizeAndGenerateDepositAddress(quote.reviewDigest)` is necessary to enable an EIP-712 request. The provider wrapper only permits the exact `feeApproval` schema for Sepolia and the pinned LBTC token, with the reviewed maximum fee and bounded expiry; it blocks arbitrary transactions, personal signing, other typed-data domains and wrong accounts. The recovered signer and account/network are checked again after signing. Existing SDK fee signatures receive the same independent validation before they can be reused. [Fee authorization semantics](https://docs.lombard.finance/build/agents/fee-authorization).

A deposit address can only come from the official SDK address-generation API with the exact cryptographically verified fee signature and typed data. A fresh signature can be used when the API acknowledges matching expiry but omits its bytes; an unknown cached signature cannot. Its current API record must match recipient, test partner, Ethereum/Sepolia environment, token and non-deprecated status. Caller-supplied addresses are never accepted. The address instruction remains Signet-only and cannot broadcast BTC. Records missing required token identity fail closed even if an older API accepts them. The fee authorization is reusable until expiry; closing the local session does not revoke an already stored protocol signature. [Deposit-address concepts](https://docs.lombard.finance/build/sdk/concepts/btc-deposit-addresses).

## Validation and evidence

Run `npm ci`, `npm run build`, `npm test` in `integrations/bitcoin`. Run `npm run check:live` for read-only network verification. The bounded public report is [live-read.json](../../integrations/bitcoin/reports/live-read.json); it contains no user positions or private keys. On the recorded run both protocols returned live reads: Babylon parameter version 6 with nine covenant keys/quorum six and a 30-confirmation staking requirement; Lombard returned its sandbox token/fee/ratio. The report explicitly identifies the dummy recipient's mocked wallet account/network reads and the fact that authorization/funding/redemption were not performed.

The package suite has **52 tests**, including **100 generated SDK stake amount/fee cases** and **500 integer satoshi roundtrips**. It checks real SDK PSBT construction and local deterministic test signatures, modified outputs/UTXOs, wrong chains/accounts, key collisions, stale contexts, jailed providers, timelocks, fee increases, altered EIP-712 schema, reused signatures, foreign deposit records, review expiry/disposal and external handoff boundaries. Seven frontend tests independently enforce disconnected, error, preparation, incomplete-service blocking, explicit authorization, and wallet guidance states. These are internal tests, not an independent audit.

Public HTTPS RPC/API responses are trusted observations, not SPV or independently verified consensus proofs. Wallet event support varies; the final package checks wallet account/network around awaited signing operations in addition to UI resets. The application never handles a user's signing key.

## Dependency audit

The package lock pins current compatible releases. [npm-audit.json](../../integrations/bitcoin/reports/npm-audit.json) records **9 low findings**, all propagated from one elliptic timing-risk advisory, [GHSA-848j-6mx2-7j84](https://github.com/advisories/GHSA-848j-6mx2-7j84), through the required Lombard LayerZero peer (`@layerzerolabs/lz-v2-utilities@3.0.168` → ethers 5.8.0 → elliptic 6.6.1). No fixed compatible elliptic/ethers version was published at this verification. npm's suggested LayerZero/SDK major downgrade violates current SDK peers and was not applied. There are no moderate/high/critical findings in this package report. Bridge operations and in-process EVM private-key signing are outside the implemented route; this reduces exposure but does not erase the advisory. Track and retest an upstream-compatible fix before production approval.

## External custody sources

Solv describes FROST threshold custody and destination-chain mapped tokens; strategy vaults add their own risk. A currently supported public end-to-end test route was not verified, so the package returns a fixed official information handoff, never an invented address or unverified bridge endpoint. [Custody architecture](https://docs.solv.finance/solvbtc-technical-architecture/bitcoin-mainnet-architecture), [strategy breakdown](https://docs.solv.finance/key-products/solv-vaults-lsts/breakdown-of-solv-vaults).

## Live sandbox findings and remaining blockers

The real test revealed the SDK catalog/resolver discrepancy before any signature was permitted. At Sepolia block **11,820,471**, public RPC independently verified both contracts' bytecode, names, symbols, decimals, EIP-712 domains, implementation addresses and implementation code hashes. The executing `0x107…` domain matches chain 11155111, name `Lombard Staked Bitcoin`, version `1`, and that verifying contract. [Pinned deployment evidence](../../integrations/bitcoin/reports/lombard-sepolia-deployments.json), [SDK discrepancy evidence](../../integrations/bitcoin/reports/lombard-sdk-address-discrepancy.json). The official [deployment registry](https://docs.lombard.finance/learn/transparency/smart-contracts) has no Sepolia entry; the test token identity therefore relies on the pinned official SDK resolver and the independent RPC observations. This proves the observed test deployment identity; it is not a governance audit or production approval.

The official testnet endpoint `https://gastald-testnet.prod.lombard-fi.com/api/v1/claimer/get-user-signature` currently returns HTTP 200 with `{}`. The SDK maps this to undefined authorization state and its write helper does not establish successful persistence. Two isolated, newly generated test-only EVM identities each signed one bounded fee authorization during this investigation; **no BTC/EVM transaction was broadcast and no deposit address was accepted**. The final implementation detects incomplete service status during quote preparation, sets `authorizationReady:false`, shows the reason, and blocks the next signature. [Raw endpoint evidence](../../integrations/bitcoin/reports/lombard-sandbox-api.json), [final blocked run](../../integrations/bitcoin/reports/lombard-address-registration.json), [earlier isolated test attempt](../../integrations/bitcoin/reports/lombard-authorization-attempt.json). No private keys or signature bytes are included in these reports.

New testnet keys were generated outside the repository, then consolidated in persistent operator-only local storage (directory mode 0700, key file mode 0600) so a later faucet transfer remains recoverable. Temporary plaintext copies were removed after the durable file was saved; its location is documented in the private operator notes, not in a browser or public evidence. Report files contain public addresses only. The official TBV faucet accepted the new Signet Taproot address but required CAPTCHA before sending coins. Other documented faucet attempts encountered a gateway failure, disconnected configuration, login, or uncompleted challenge. No challenge was bypassed or account created. Public RPC checks found no Signet UTXOs and no BABY balance in these new accounts. [Faucet and balance evidence](../../integrations/bitcoin/reports/faucet-attempts.json). A funded Babylon staking/unbonding lifecycle therefore remains unverified; the earlier read-only report remains labelled as such.

Browser checks exercised real Babylon discovery and the Lombard SDK quote in both production preview and the final development preview. The Lombard browser used a mocked provider for public account/network reads only, with real protocol RPC/API responses; the service block remained visible and authorization stayed disabled even after risk acknowledgement. No signing request was issued. Both desktop and 375px mobile rendered without a horizontal overflow or page exception. [Browser evidence and two screenshots](../../integrations/bitcoin/reports/ui/). An earlier development-server attempt encountered an outdated Vite optimizer dependency; per-network caches and a clean restart resolved the issue before the final recorded run.
